يشغل الحاويات في Pods

🔄 قصة حياة أي طلب في Kubernetes:

  • 1️⃣أنت تطلب: `kubectl apply -f pod.yaml` — الطلب يذهب مباشرة إلى الـ API Server.
  • 2️⃣الحفظ: الـ API Server يراجع الصلاحيات ويحفظ هذا الطلب في الـ etcd (ذاكرة العنقود).
  • 3️⃣التوزيع: الـ Scheduler يلاحظ وجود Pod جديد بلا عنوان، فيبحث عن أفضل Node ليضع الـ Pod فيها.
  • 4️⃣التنفيذ: الـ Kubelet الموجود على الـ Node يقرأ الأوامر من الـ API Server ويطلب من Docker تشغيل الحاوية!

🧠 تفصيل مكونات الـ Control Plane

Kube-API Server 🚪

البوابة الرئيسية. أي شيء في K8s (حتى المكونات الداخلية) يجب أن تتحدث معه. لا يوجد تواصل مباشر بين المكونات الأخرى.

etcd 🗄️

قاعدة بيانات (Key-Value) عالية الموثوقية تخزن الـ State الخاصة بالـ Cluster. بدونها Kubernetes يفقد الذاكرة بالكامل.

Kube-Scheduler 📅

يقرر "أين" ستعمل الـ Pods بناءً على الموارد المتاحة (CPU/RAM) وقواعد التوزيع (Affinities).

Controller-Manager 👮

يراقب باستمرار لضمان أن الحالة الحالية (Current State) تطابق المطلوبة (Desired). مثلاً إذا وقع Pod يقوم بإنشاء غيره فوراً.

⚙️ تفصيل مكونات الـ Worker Node

Kubelet 🤖

الوكيل (Agent) الذي يتحدث مع الـ API Server. يأخذ أوامر "شغّل هذا الـ Pod" ويقوم بالتنفيذ، ويرسل تقرير مستمر عن صحة الحاويات.

Kube-Proxy 🔀

يدير قواعد الشبكة (Network Rules) والتوجيه. هو المسؤول عن جعل الـ Services قادرة على توزيع المرور (Load Balancing) بين الـ Pods.

Container Runtime 🐳

البرنامج الذي يقوم بتشغيل الحاويات فعلياً (مثل containerd أو Docker أو CRI-O).

📦 ما هو الـ Pod في Kubernetes Documentation؟

بحسب توثيق K8s الرسمي، الـ Pod هو "أصغر وحدة حوسبة قابلة للنشر". الـ Pod مثل "غلاف طماطم" يضم بداخله حاوية واحدة أو أكثر يتشاركون نفس الـ Storage والـ Network (كلهم يتحدثون بـ localhost).

🚀 ما هو Minikube؟

بيئة Kubernetes المحلية

يجمع Minikube كل المكونات السابقة (Control Plane + Worker Node) ويضعها معاً في جهاز افتراضي واحد أو حاوية Docker واحدة.

  • 💻ممتاز للتعلم السريع والتجربة دون تكلفة.
  • ⚙️يتيح لك استخدام أمر `kubectl` كأنك تدير Production.
# أوامر Minikube الأساسية
minikube start # لإنشاء وبدء الـ Cluster
minikube status # التأكد أن الـ Control Plane يعمل
minikube stop # إيقافه مؤقتاً لتوفير موارد جهازك
minikube dashboard # فتح لوحة التحكم البصرية للمراقبة

🎯 تاسكات الـ Pods المتوقعة والأهم

1️⃣ الإنشاء والاستعلام (Create & Get)

kubectl run my-nginx --image=nginx
kubectl get pods # يعرض الحالة هل هي Running أم Pending

2️⃣ الفحص والتشخيص (Describe)

إذا كان الـ Pod عالقاً في Pending أو CrashLoopBackOff، استخدم Describe لقراءة الـ Events (الأحداث التي يكتبها الـ Kubelet و Scheduler).

kubectl describe pod my-nginx

3️⃣ قراءة السجلات (Logs)

لرؤية الـ output الخاص بالتطبيق نفسه (مثلا أخطاء البرمجة أو 500 Errors).

kubectl logs my-nginx

4️⃣ الدخول إلى الحاوية الحية (Exec)

يُطلب منك كثيراً الدخول للـ Pod لعمل Ping أو مراجعة إعدادات. هذا مثل SSH للـ Container!

kubectl exec -it my-nginx -- /bin/bash

5️⃣ كشف البورت محلياً (Port Forwarding)

لو أردت فتح الـ Pod في متصفح جهازك بسرعة دون تعقيدات الخدمات (Services).

kubectl port-forward pod/my-nginx 8080:80

💡 سؤال انترفيو خطير:

"لو مسحنا الـ Pod باستخدام `kubectl delete`، هل سيرجع مرة أخرى؟"

الجواب: لا! الـ Pod المباشر يموت بلا رجعة. ولهذا في بيئات العمل الحقيقية لا ننشيء Pods بل ننشيء Deployments وهي بدورها تصنع وتحافظ على الـ Pods!
